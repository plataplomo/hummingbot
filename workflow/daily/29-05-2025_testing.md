
**Prompt for AI Coder (Angel): Integrate Refactorings and Fix Pytest Errors in `tests/unit/apis/`**

**Project:** CyberDeltaEngine
**Context:**
We have recently completed a significant refactoring of the `cyberdelta/apis/backpack/` components. This included:
1.  A major rework of Backpack authentication to correctly use ED25519 (initially mistaken for SHA-based). This impacts `bp_auth.py` and its usage in `bp_api.py`.
2.  Introduction and refinement of numerous Pydantic models for raw API request and response payloads across the `cyberdelta/apis/backpack/models/` directory (e.g., for orders, fills, market data, errors, common raw types).
3.  Definition of Pydantic models for Backpack WebSocket subscription request payloads (`BackpackRawWsSubscriptionRequest`) and the related flow involving `BackpackAPI._construct_subscription_payload` and `BackpackWsMessageRouter.construct_subscription_payload`.
4.  Updates to `IAuthenticator` and `HttpClient` interfaces and implementations to enforce stricter string-based header typing.

The primary goal of these Pydantic models is to strictly define and validate the data crossing API boundaries, ensuring type safety and adherence to the expected data structures. **Crucially, the existing business logic within services, mappers, and the main API client (`bp_api.py`) should be treated as the source of truth for *what* data is expected and *how* it's processed.** The Pydantic models are there to enforce this contract, not to redefine it.

**Goal:**
Run the pytest unit tests located in the `tests/unit/apis/` directory. Identify and fix all errors and failures, ensuring that the recent refactorings and Pydantic model updates are correctly integrated and that the tests pass while respecting the existing business logic.

**Why:**
This step is critical to:
1.  Verify the correctness of our Pydantic models against the actual data flow.
2.  Ensure the refactored authentication and API components function as intended.
3.  Catch any regressions or new issues introduced during the refactoring.
4.  Maintain adherence to our project rules (Static Analysis V3, Runtime Safety V3, No Silencing V4, Model Architecture V1).

**What to do (Step-by-Step):**

1.  **Run Pytests:**
    *   Execute `pytest tests/unit/apis/`.
    *   Collect all error messages and tracebacks.

2.  **Analyze Failures:**
    *   For each failure, determine the root cause. It could be:
        *   **Pydantic Validation Errors:** The Pydantic model (e.g., a `BackpackRaw...` model in a response handler or a request payload model in a request builder) is expecting a different structure/type than what the code (or test mock) is providing.
        *   **TypeErrors:** Mismatches due to stricter typing enforced by the refactored components or new models.
        *   **AssertionErrors:** Test assertions are failing because the behavior of the code under test has changed, or the expected outcome in the test is no longer correct due to the refactoring.
        *   **AttributeErrors/KeyErrors:** Code might be trying to access fields that have been renamed, removed, or are not present in the way Pydantic models now structure the data.
        *   **Authentication Logic Errors:** Signatures might be failing, or required authentication components might be missing/incorrectly configured in tests.

3.  **Fix Errors (Prioritize as follows):**
    *   **Guideline:** The existing business logic (how data is used in mappers, services, API methods *before* it hits a Pydantic model for validation, or *after* it comes out of one) is the primary source of truth for data structures.
    *   **Pydantic Model Adjustments:**
        *   If a Pydantic model (e.g., `BackpackRawOrder`, `BackpackRawWsSubscriptionRequest`, `AuthenticatedRequestComponents`) is causing validation errors because its definition (fields, types, aliases, validators, `Field` constraints) does not accurately reflect the data structure being passed to it by existing logic or expected by the external API, **adjust the Pydantic model to match the data.**
        *   This includes ensuring `Field(alias="...")` correctly maps to JSON keys, default values are appropriate, and types (`RawBp...` common types) are correctly applied.
    *   **Data Transformation Adjustments (Minimal):**
        *   If raw data fetched from an API (or mocked in a test) needs *minor* and logically sound adjustments *before* being validated by a Pydantic model (e.g., converting a known string "null" to actual `None`, or a slight re-keying that doesn't change meaning), this is acceptable.
        *   **Do NOT fundamentally change the business logic or the data's meaning to fit a Pydantic model.**
    *   **Test Data/Mock Updates:**
        *   If tests are failing because their mock data or expected outputs no longer align with the *correctly refactored and Pydantic-modeled* code, update the tests and their mocks. For example, if a Pydantic model now correctly enforces that a field cannot be `None` and a test was previously expecting `None`, the test's mock data should be updated.
    *   **Code Logic Fixes:**
        *   If the refactoring introduced actual bugs (e.g., incorrect variable usage, flawed logic in authentication, incorrect data flow), fix these bugs.
    *   **Authentication Flow:** Pay close attention to tests involving authenticated requests. Ensure the `BackpackEd25519Authenticator` is being used correctly in tests and that mocked API secrets/keys are appropriate.

4.  **Iterate:**
    *   After applying fixes, re-run `pytest tests/unit/apis/`.
    *   Repeat the analysis and fixing process until all tests in this directory pass.

5.  **Project Rule Adherence:**
    *   All fixes MUST strictly adhere to:
        *   Static Analysis V3
        *   Runtime Safety V3
        *   No Silencing V4 (do not use `# type: ignore` or similar without extreme justification and noting it for review)
        *   Model Architecture V1 (Raw/Internal model separation, Pydantic for boundaries)
        *   Config Integrity V3

6.  **Reporting:**
    *   List all files modified.
    *   Report the output of static analysis tools (Mypy, Pylint, Ruff) after changes.
    *   Clearly state that all tests in `tests/unit/apis/` are passing.
    *   If any changes were made that might subtly alter business logic (even if to match a "more correct" Pydantic model), highlight these for human review.
