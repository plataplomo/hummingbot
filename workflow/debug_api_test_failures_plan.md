## Overarching Principles:

*   **Models are Immutable:** Pydantic models in the following directories **must not be changed**:
    *   `cyberdelta/apis/models/`
    *   `cyberdelta/apis/backpack/models/`
    *   `cyberdelta/apis/hyperliquid/models/`
    Fixes must occur in test data, test assertions, or data handling logic *before* Pydantic validation.
*   **OpenAPI Specs as Reference:** The OpenAPI specifications ([`openapi_backpack.json`](openapi_backpack.json) and [`openapi_hl.json`](openapi_hl.json)) can be consulted to understand intended API contracts, but the Pydantic models remain the ultimate source of truth for data structure if discrepancies arise.
*   **Iterative Approach:** Fix one category or file of tests, re-run relevant tests to observe the impact, and then proceed. One fix might resolve multiple failures or expose new underlying issues.

## Phase 1: Deep Dive into Backpack Pydantic Validation Failures (`tests/unit/apis/backpack/test_bp_response_handler.py`)

This test file has a high concentration of reported failures and explicitly tests Pydantic validation logic. Understanding and resolving these is critical.

*   **Step 1.1: Analyze `test_handler_validation_error_dict` Failures (Backpack)**
    *   **Objective:** Identify and rectify mismatches between how tests *modify* valid data (from fixtures like `valid_raw_ticker`) to create invalid scenarios, and the Pydantic `ValidationError`s that result when `BackpackResponseHandler` methods (e.g., `handle_get_ticker_response`) attempt to validate this modified data against the immutable Backpack Pydantic models.
    *   **Actions (for Angel):**
        1.  Focus on the `_validation_error_test_cases_dict` parameterization (around line 801 in [`tests/unit/apis/backpack/test_bp_response_handler.py`](tests/unit/apis/backpack/test_bp_response_handler.py:801)).
        2.  For each failing test case generated by this parameterization:
            *   Identify the `handler_method`, base `fixture_name`, and `modification_details` (e.g., `missing_field`, `invalid_field_type`, `extra_field`).
            *   Manually inspect (or use a debugger) the `modified_data` that is generated by applying `modification_details` to the data from `fixture_name`.
            *   Compare this `modified_data` structure against the corresponding Pydantic model (e.g., if `fixture_name` is `valid_raw_ticker`, compare against `BackpackRawTicker` found in [`cyberdelta/apis/backpack/models/bp_raw_market.py`](cyberdelta/apis/backpack/models/bp_raw_market.py:111-126)).
            *   Run the specific `handler_method` with this `modified_data` in isolation (e.g., using a debugger or a scratch script) and inspect the actual `ValidationError` raised by Pydantic (specifically examine the output of `e.errors()`).
            *   Compare the actual `e.errors()` details with the `expected_error_substring` and `context_string` used in the failing test's assertion.
            *   **Fix Strategy:**
                *   If the `modification_details` in the test no longer accurately create the intended invalid scenario for the *current, immutable* model, adjust the `modification_details`.
                *   If the modification is still relevant but Pydantic's error reporting details (message, path, type) have changed, adjust the `expected_error_substring` in the test assertion to match the actual Pydantic error.
                *   **Crucially, do not change the Pydantic model itself.**
    *   **Expected Outcome:** Tests driven by `_validation_error_test_cases_dict` should pass. The test modifications should now correctly reflect scenarios that are expected to fail validation against the immutable models, and the test assertions should accurately match Pydantic's actual error outputs for those scenarios.

*   **Step 1.2: Analyze `test_handler_list_item_errors` Failures (Backpack)**
    *   **Objective:** Similar to Step 1.1, but specifically for tests that process lists of items. Ensure that modifications to individual list items cause the expected validation errors or warnings, and that test assertions reflect these.
    *   **Actions (for Angel):**
        1.  Focus on the `_list_item_error_cases` parameterization (around line 956 in [`tests/unit/apis/backpack/test_bp_response_handler.py`](tests/unit/apis/backpack/test_bp_response_handler.py:956)).
        2.  For each failing case:
            *   Inspect the `fixture_name_for_list` and the `modification_details` that are applied to an item within that list.
            *   Validate the modified list item against its Pydantic model in isolation.
            *   Check if the test expects a warning log (indicated by `is_warning_expected=True`) or an `APIError`. Compare this expectation with the actual behavior of the handler method when it processes the malformed list.
            *   Compare the actual error message or log content with the `expected_substring` in the test assertion.
            *   **Fix Strategy:** Adjust `modification_details`, `expected_substring`, or `is_warning_expected` in the test assertions as needed. **Do not alter the Pydantic models.**
    *   **Expected Outcome:** Tests driven by `_list_item_error_cases` should pass.

*   **Step 1.3: Analyze `test_handler_invalid_top_level_type` Failures (Backpack)**
    *   **Objective:** Ensure that tests passing incorrect top-level data types (e.g., providing a list where a dictionary is expected by a handler method) produce the correct `APIError`, and that assertions match.
    *   **Actions (for Angel):**
        1.  Focus on the `_invalid_type_test_cases` parameterization (around line 633 in [`tests/unit/apis/backpack/test_bp_response_handler.py`](tests/unit/apis/backpack/test_bp_response_handler.py:633)).
        2.  For failing cases, verify if the `APIError` raised by the handler (which usually performs an `isinstance` check before Pydantic validation, e.g., [`handle_get_ticker_response`](cyberdelta/apis/backpack/bp_response_handler.py:75-80)) matches the `expected_error_message_substring` in the assertion.
            *   **Fix Strategy:** Adjust the `expected_error_message_substring` in test assertions if the error message generated by the handler for a top-level type mismatch has changed.
    *   **Expected Outcome:** Tests driven by `_invalid_type_test_cases` should pass.

*   **Step 2.2: Analyze Hyperliquid Test Fixtures vs. Immutable Models**
    *   **Objective:** For each failing Hyperliquid test identified, compare the structure and content of the test fixture data against the definitions in the (immutable) Hyperliquid Pydantic models.

                *   If a *required* field is missing from a test fixture: **Add the field to the test fixture** with a valid default or example value that aligns with the model's type definition.

                *   **Do not change the Pydantic model definitions.**
    *   **Expected Outcome:** Pydantic validation errors for Hyperliquid tests are resolved by ensuring test fixtures and data align strictly with the existing, immutable model definitions.

## Phase 4: Tackle HTTP Client Failures (`tests/unit/apis/connectivity/test_http_client.py`)

Failures in the HTTP client (`FFF.F`) are fundamental and could be the root cause of, or contribute to, other cascading issues.

*   **Step 4.1: Analyze HTTP Client Test Failures**
    *   **Objective:** Understand why tests for the HTTP client ([`cyberdelta/apis/connectivity/http_client.py`](cyberdelta/apis/connectivity/http_client.py)) are failing. These tests likely involve mocking external HTTP calls (e.g., using `pytest-mock` or `aiohttp.testing.mockserver`) and asserting the client's behavior regarding retries, error handling, and basic response processing before data reaches more specific handlers like `BackpackResponseHandler`.
    *   **Actions (for Angel):**
        1.  Examine the failing tests in [`tests/unit/apis/connectivity/test_http_client.py`](tests/unit/apis/connectivity/test_http_client.py).
        2.  Determine if failures are due to:
            *   **Incorrect Mock Setup:** The mock server or patched HTTP calls are not returning the responses/status codes that the test expects the HTTP client to handle.
            *   **Changes in HTTP Client Logic:** The HTTP client's internal logic (e.g., how it interprets status codes, handles timeouts, extracts initial response data, or manages retries) may have changed or contain bugs. This is distinct from Pydantic model validation, which happens later.
            *   **Outdated Assertions:** The test assertions no longer accurately reflect the HTTP client's current (and possibly correct) behavior.
        3.  **Fix Strategy:** Correct mock setups to provide the appropriate test conditions. If the HTTP client has bugs unrelated to the immutable Pydantic model constraints, fix the client logic. Otherwise, update test assertions to match the client's correct operational behavior.
    *   **Expected Outcome:** Tests in `test_http_client.py` should pass, ensuring that the foundational layer for making API calls is reliable and behaves as expected under various network conditions and server responses.
